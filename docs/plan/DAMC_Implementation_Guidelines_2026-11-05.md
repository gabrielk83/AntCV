## 1. Purpose, scope, non-goals

### 1.1 Purpose

DAMC reads project-management and hardware-process documents on the company OneDrive. It checks them for factual integrity, internal consistency, process completeness, language quality and regulatory references. It reports findings to a human reviewer. It runs on one controlled local machine. Human-authored source documents are read-only. The one exception: files generated by company tools (DAMC itself or another registered tool) may be created and updated, under the guards in Section 7.8.

### 1.2 In scope

| Area | Document types |
|---|---|
| Project management | Charter, project plan, schedule exports, RAID log (risks, assumptions, issues, dependencies), status reports, minutes, decision log, change requests, SOW and contract metadata, lessons learned |
| Hardware technology process | Requirements, specifications, drawing metadata, BOM, DFMEA/PFMEA, control plans, test plans and reports, ECR/ECO/ECN, gate review packs, qualification reports, supplier documents (FAI, PPAP, certificates) |
| Languages | English, Danish, Swedish, Norwegian (Bokmål, Nynorsk), Finnish. Icelandic: detect only until a reviewer exists. |
| International content | EU, UK, US, China, Japan, South Korea, India, South-East Asia, LATAM (Brazil, Mexico, Argentina, Chile, Colombia). Others added only through the mandatory scope expansion step (Section 11.4). |
| Cadence | Monthly scan and review cycle. On-demand scan for one project. |

### 1.3 Non-goals (hard limits)

These are design constraints. The architecture MUST make them impossible, not only discouraged.

| ID | Non-goal | Reason |
|---|---|---|
| NG-1 | No scoring, ranking, profiling or performance monitoring of individual people. Findings attach to documents and roles, never to a named person's performance. | Keeps the system out of AI Act Annex III point 4 (employment, worker monitoring, task allocation by behaviour). Avoids GDPR Art. 22 effects. National co-determination rules on control measures. |
| NG-2 | No emotion, sentiment or stress inference on staff text. | AI Act Art. 5(1)(f): emotion recognition in the workplace is prohibited (medical and safety reasons excepted). |
| NG-3 | No edits, deletions, moves, renames or permission changes on human-authored OneDrive files. Exception: files in the generated-file registry (SEC-28) may be updated by the tool that owns them. Permission changes are never allowed, on any file. | Sources untouched; tool outputs maintainable. |
| NG-4 | No sending, posting or publishing. The tool writes one signed report to one restricted folder. | Human decides distribution. |
| NG-5 | No GDPR Art. 9 special-category data, national ID numbers or export-controlled technical data sent to any LLM tier. | Data minimisation and export control. |
| NG-6 | No legal advice. Regulatory findings are flags for a qualified reviewer. | Liability. |

## 2. Operating environment

### 2.1 Constraints

- **ENV-01** MUST run on a company-owned, managed Windows device: device management enrolled, BitLocker on, EDR active, local admin rights removed from the operator account.
- **ENV-02** Data source is the company OneDrive / SharePoint. Two connector options:
  - **Option A (phase 1, recommended):** read from the OneDrive sync client folder. No new app registration. The analysis processes get read-only file system rights on the synced project folders. Writes go only through the guarded writer (Section 7.8), a separate process.
  - **Option B (phase 5):** Microsoft Graph with delegated permissions and selected-scope access (per-site or per-file grants, e.g. `Sites.Selected` or the `*.SelectedOperations.Selected` family `[C]`). Needed for version history, eTag-based delta scans and sensitivity-label metadata. Write grants are per generated file, never per folder or site.
  - **MUST NOT** use tenant-wide application permissions such as `Files.Read.All` or `Sites.Read.All`.
- **ENV-03** Network egress default-deny. Allowlist only: Microsoft 365 endpoints for OneDrive sync, the approved enterprise LLM endpoint (only if Tier 2 is approved), and nothing else. Mirror refresh happens on a separate connected step (Section 9.4). An empty allowlist means deny all, never allow all. (AntCV: the relay's CORS code fell back to `*` when its origin list was empty.)
- **ENV-04** Tier 1 runs a local model with no network access. Consumer AI apps and AI browser extensions are blocked.
- **ENV-05** Closed coding environment: development on the same or a sibling managed device. Packages and model weights come from the internal mirror (Section 9, mirror M7). No direct pulls from public registries at build time.

### 2.2 Trust zones and data flow

```
Zone A  OneDrive / SharePoint (source of record)             read-only, except registered tool-generated files
   |    sync folder (Option A) or Graph delegated, selected scope (Option B)
Zone B  Intake quarantine                                    parse only, never execute
   |    sanitised text + structure + SHA-256 per file and per span
Zone C  Analysis core
   |      Tier 0  rules engine, deterministic (no LLM)       always on
   |      Tier 1  local LLM, no network, no tools            on after Phase 3 gate
   |      Tier 2  enterprise LLM, EU region, DPA in place    OFF by default
Zone D  Local mirrors (reference data)                       read-only, hashed, dated
Zone E  Evidence store: findings, run log, fact register     encrypted, append-only log
   |    human review and sign-off
Zone F  Report folder on OneDrive (restricted group)         default write target
        + registered tool-generated files in Zone A          via the guarded writer only
```

Rules:

- **ENV-06** Data moves down the zones only. Nothing in Zone C writes to Zone A directly. Every write goes through the guarded writer (Section 7.8).
- **ENV-07** Zone F is the default write target. The only other targets are files in the generated-file registry owned by the writing tool. Writes anywhere else are refused and logged.
- **ENV-08** Document text never leaves the device except inside a signed report placed in Zone F.

## 3. Design principles

Each principle comes from a failure or a working control in AntCV.

| ID | Principle | AntCV origin |
|---|---|---|
| P1 | **Source of record first.** A finding exists only when tied to a source span. Build from the authoritative record, never from a re-typed or exported copy. | Deliverable built from a lossy export dropped mandatory content (AntCV: `docs/qa/DELIVERABLE_PREFLIGHT_CHECKLIST.md`) |
| P2 | **Gate facts in code, not by asking a model.** Numbers, dates, IDs and units are checked deterministically against the source. | SOURCE-FRACTURES-001 (`workers/proxy/src/source-fractures.js`) |
| P3 | **Prompt rules are not controls.** A rule the model broke once gets a deterministic check, not more prompt text. | Model broke three prompt bans in one sentence (PROFILE-ACCESS-SCRUB-001, GEN-LANGFAB-001) |
| P4 | **Fail loud, never fill.** Missing data returns null plus a visible "needs input" flag. Abstaining is a correct answer. | JD analysis `grounded:false` + assumptions list (`workers/demo-proxy/src/jd-analysis.js`); JD-SCAN-HALLUCINATION-001 |
| P5 | **The checker must not read like the writer.** Verification uses a different model family and a different ordering of the source. | Writer and checker read the same prose in the same order, so a hallucination looked plausible to both (SOURCE-FRACTURES-001) |
| P6 | **Measure, don't eyeball. A green check must be able to see red.** Every check has a negative control that proves it can fail. | False green from a blind audit; negative-control tests (`docs/qa/ACTIVE_BUGS.md`) |
| P7 | **Guard every write.** Refuse writes outside the tool's own folder, stale writes and shrinking writes. | Shrink guard, revision guard 409, APP-ROW-WRITE-GUARD (`pwa/antcv-cloud-put-shrink-guard-289.js`, `pwa/antcv-app-rev-guard.js`) |
| P8 | **Diagnose first.** Reproduce, probe, then a targeted fix. No speculative changes. | v1.40.335 fetch-wrapper incident (CLAUDE.md, hotfix discipline) |
| P9 | **Identity gate before any rebuild.** A rebuilt or refactored component must produce identical output on the gold set before release. | APPJS-BLUESCREEN-001 (`docs/deployment/app-js-source-and-rebuild.md`) |
| P10 | **One lane, one deployer, never force.** Claimed version ranges, sync first, no parallel deploys. | Parallel session reverted a confirmed fix (`docs/qa/NIGHT_SHIFT.md`) |
| P11 | **A run that only lives in chat did not happen.** Every run writes start and end heartbeats and a register entry. | Silent no-op runs (`docs/qa/SCHEDULED_ROUTINES.md`) |
| P12 | **Log the run, not the content.** Metadata and hashes in logs. Document text never in logs. | llm_calls telemetry pattern (Section 17.3) |
| P13 | **A person signs.** No finding leaves the device without a named reviewer role. | Every AntCV output engineer- or owner-approved; production writes owner-gated |

## 4. Reference architecture

### 4.1 Components

| ID | Component | Job | Key controls |
|---|---|---|---|
| C1 | Connector | Lists and reads files from Zone A | Read-only rights. Writes only through the guarded writer (Section 7.8). Path allowlist per project. Records file ID, path, version/eTag, modified time, sensitivity label. |
| C2 | Intake and quarantine | Converts files to text + structure | File-type allowlist. Size and page limits. Macros never run. No external references fetched. OCR for scans. Low-privilege process with no network. |
| C3 | Classifier | Document type, language, sensitivity, special data | PII and national-ID detector, export-control marker detector, special-category detector. Routing decision per document: Tier 0 only / Tier 1 allowed / Tier 2 allowed. |
| C4 | Extractor | Deterministic entities with span references | Dates, durations, money, quantities with units, requirement IDs, part numbers, revisions, ECO numbers, roles, organisation IDs. |
| C5 | Fact register ("project kernel") | Baseline facts per project | Each fact: value, source span, role owner, valid-from, status (proposed / confirmed / superseded). Changes only through review. |
| C6 | Check engine | Runs rule packs | Packs: PM (Section 12), HW (Section 13), locale (Sections 10–11), style (Section 8.6). Each check versioned. |
| C7 | LLM gateway | The only path to any model | Tier routing from C3. Redaction before send. Versioned prompt templates. JSON-schema output validation. Budget caps. No tools, no network for Tier 1. |
| C8 | Verifier | Checks every generated claim | Span-hash match, numeric fidelity, cross-family entailment, cross-document consistency, freshness. |
| C9 | Mirror manager | Reference data in Zone D | Manifest, hashes, licence, freshness. Integrity check at run start. |
| C10 | Locale module | Language and region rules | Language ID, number/date/currency parsers per locale, glossary, registry-ID validators. |
| C11 | Review console | Local UI for reviewers | Accept / reject / downgrade with reason. Cannot upgrade a label without new evidence (QA-07). |
| C12 | Report and evidence generator | Signed outputs | Run report, finding list, evidence pack, AI disclosure, machine-readable AI marker. |
| C13 | Scheduler | Monthly and on-demand runs | Heartbeats. Missed-run alarm. |
| C14 | Audit log | Who did what, when | Append-only. Hash-chained. Metadata only. |
| C15 | Config | Rules, thresholds, routing | Signed config. Two-person change. Every value versioned. |

### 4.2 Processing stages per run

1. Integrity check: config signature, mirror hashes, model weight hash, gold-set hash.
2. Start heartbeat written to C14.
3. C1 lists changed files since last run (hash or eTag delta). Quarterly: full scan.
4. C2 intake. Failures are findings, not silent skips.
5. C3 classifies and routes.
6. C4 extracts. C5 compares with the fact register.
7. C6 runs Tier 0 checks.
8. C7 runs Tier 1 (and Tier 2 if approved) for summarisation and classification only.
9. C8 verifies every generated claim. Unverified claims leave the report body.
10. C11 review queue. C12 builds the report after sign-off.
11. End heartbeat. Register entry. Metrics.

## 6. EU AI Act controls

### 6.1 Classification memo (MUST exist before build)

- **Role.** If built in-house, the company is the **provider** of an AI system and also its **deployer**. The GPAI model vendor holds the GPAI model obligations.
- **Target risk class.** Not high-risk. This holds only while NG-1 and NG-2 hold. Any feature that evaluates, ranks or monitors workers, or allocates tasks based on individual behaviour or traits, moves the system into Annex III point 4 and triggers Chapter III obligations. The same reasoning appears in AntCV's own compliance file: ranking candidates for a third party would make it high-risk (AntCV: `docs/compliance/EU_AI_ACT_GDPR.md`).
- **AIA-01** Each new feature gets a one-paragraph classification check signed by the AI compliance lead before build.

### 6.2 Obligations that apply now

| ID | Article | Control |
|---|---|---|
| AIA-02 | Art. 4 AI literacy | Training for operators and reviewers before access. Record kept per person. Content: model limits, hallucination types, verification labels, NG list, incident reporting. See Section 14.3. |

Console users acknowledge an AI notice before first use; the acknowledgement is stored with notice version, timestamp and user, and asked again when the notice version changes. If a chat/Q&A feature is ever added, users are told they interact with AI. (AntCV: AI notice modal, acknowledgement stored per identity with version and timestamp.) |

## 7. Cybersecurity controls

Frameworks: ISO/IEC 27001:2022 Annex A, NIST CSF 2.0, OWASP Top 10 for LLM Applications (2025), MITRE ATLAS. NIS2 (Directive (EU) 2022/2555) applies if the company is an essential or important entity: national acts differ (Sweden: Cybersäkerhetslagen SFS 2025:1506, in force 15 Jan 2026 `[V2]`; Denmark: national NIS2 act `[C]`).

### 7.1 Threat model

**SEC-01** A STRIDE model per trust zone plus the LLM threats below. Reviewed quarterly and on any architecture change.

| Threat (OWASP LLM 2025) | Control |
|---|---|
| LLM01 Prompt injection through document content | Four layers before any model sees text: (1) strip invisible and bidirectional control characters; (2) remove hidden content (hidden runs, white-on-white text, off-page objects, hidden HTML) and record what was removed; (3) instruction-shaped patterns redacted from the LLM copy and flagged; (4) remaining text wrapped in delimiters marked as data, with length caps. LLM has no tools, no network, no write rights. Output must match a JSON schema or is discarded. Injection corpus in the gold set (Section 15.2). (AntCV: `workers/proxy/src/prompt-injection-defense.js`, POSTING-GUARD-001) |
| LLM02 Sensitive information disclosure | Redaction before LLM. Output scanned for PII. Context is per project: one project's text never enters another project's prompt (same lesson as AntCV owner facts leaking into another user's CV via shared prompt examples: EXAMPLE-ISOLATION-001). |
| LLM03 Supply chain | Model weights from an approved source, SHA-256 pinned. Packages from the internal mirror. SBOM per release. |
| LLM04 Data and model poisoning | Mirrors signed and diffed. Gold set locked (Section 15.3). No fine-tuning on unreviewed data. |
| LLM05 Improper output handling | Model output rendered as escaped plain text. Generated Office files contain no macros. No hyperlinks from model output unless the domain is allowlisted. |
| LLM06 Excessive agency | No tool calls. Read-only connector. Write guard. |
| LLM07 System prompt leakage | No secrets, paths or credentials in prompts. |
| LLM08 Vector and embedding weaknesses | Per-project index. Retrieval re-checks the reader's OneDrive permission. Index deleted with the project. |
| LLM09 Misinformation | Section 8 fact pipeline. |
| LLM10 Unbounded consumption | Per-run token, time and file-size caps. Cost cap for Tier 2. |

Non-LLM threats:

| Threat | Control |
|---|---|
| Malicious file | Parsing in a low-privilege sandboxed process with no network. Macros never run. External links and OLE objects not resolved. XML external entities off. PDF JavaScript ignored. Archive bomb and size limits. AV scan at intake. |
| Credential theft | No stored passwords. Tokens in the OS credential store (TPM-backed where possible). MFA and Conditional Access on the operator account. Short token lifetime. |
| Insider misuse | Role separation (Section 20). Every console view logged. Reviewers cannot change rules. Admins cannot sign reports. |
| Tampered evidence | Hash-chained audit log. Signed reports. Periodic chain verification. |
| Identity spoofing | User identity comes from the OS session or the identity provider token only, never from a document field, config value or header the caller supplies. (AntCV: DEMO-RELAY-IDENTITY-001 strips caller-forged identity headers.) |

- **SEC-26** Empty or unreadable input reports "no text", never "clean". A guard that saw nothing must not return a pass. (AntCV: POSTING-GUARD-001.)
- **SEC-27** Values that feed metrics or cost are computed by DAMC from raw data. Telemetry fields accept only allowlisted values. (AntCV: client-reported cost was about 3× too high; the relay now computes cost from its own rate table, FT-RELAY-COST-SOURCE.)

### 7.2 Endpoint hardening

**SEC-02** Checklist, verified at go-live and quarterly: BitLocker, EDR, application allowlisting (WDAC/AppLocker), no local admin for the operator, host firewall egress allowlist, USB storage blocked, screen lock, OS and runtime patch SLA (critical: 14 days or company policy), no remote desktop from outside the corporate network.

### 7.3 Identity and access

- **SEC-03** Operator and reviewer access through a dedicated security group. MFA required.
- **SEC-04** Connector uses the operator's delegated rights (Option A/B). DAMC never sees more than the operator could open.
- **SEC-05** Unattended monthly runs (phase 5 only): app-only access limited to named sites via selected-scope grants, certificate credential in a TPM-backed store, rotated per company policy. Until then a person starts each run.
- **SEC-06** Quarterly access review. Leavers removed same day.

### 7.4 Secrets

- **SEC-07** No secrets in code, config files, prompts or logs. OS credential store or the company vault only.
- **SEC-08** Pre-commit secret scanning in the repo. Any hit blocks the commit.
- **SEC-09** Token-expiry check at every run start. AntCV lost 27 days to a dead access token after a 33-day dispatch gap (AntCV: `docs/qa/SCHEDULED_ROUTINES.md`).

### 7.5 Secure development

- **SEC-10** Protected main branch. Two-person review. No force push. Sync first, claim a lane, one deployer (P10).
- **SEC-11** SAST, dependency scan and licence scan on every change. SBOM (CycloneDX or SPDX) per release. Weekly dependency audit separates runtime from dev dependencies; critical findings alert the CISO role; nothing is upgraded without approval and the identity gate. (AntCV: SECURITY-WEEKLY-001, `docs/security/SECURITY_UPDATE_POLICY.md`.)
- **SEC-12** Signed release artifacts. Reproducible build where the toolchain allows.
- **SEC-13** Identity gate: any rebuild, refactor, minification or dependency upgrade must reproduce gold-set outputs exactly before release (P9). A failure blocks the release (Section 15.4, gate 4).
- **SEC-14** Known-unsafe tooling register: tools proven to change behaviour (AntCV: the esbuild minifier added `"use strict"` and broke a sloppy-mode bundle) are listed and blocked until they pass the identity gate.
- **SEC-15** Dead-file check: before editing a component, confirm it is actually loaded/active. AntCV had retired scripts on disk that were no longer loaded; edits to them were no-ops, and one feature shipped dead. An automated "components live" check runs in QA and fails when a declared component is not loaded. (AntCV: `scripts/qa-checks.mjs`.)

### 7.6 Logging and monitoring

- **SEC-16** Logged: run ID, start/end, user (keyed hash, not the account name), files (ID + hash, not content), checks run, model and prompt versions, token counts, verdict counts, reviewer actions, config changes, errors. Logging never blocks or slows analysis: a failed log write is itself logged locally and alarmed, and has a time limit. (AntCV: LLM-LOG-SERVER-001 logs metadata only, never throws, and is time-capped; user ids are SHA-256 hashes.)
- **SEC-17** Not logged: document text, extracted values, prompts with content, model outputs. These stay encrypted in Zone E.
- **SEC-18** Security events (integrity failures, blocked egress, guard refusals, injection hits) go to the SIEM as metadata.

### 7.7 Backup, recovery, kill switch

- **SEC-19** Zone E backed up encrypted. Restore tested quarterly.
- **SEC-20** Kill switch: one config flag drops all runs to Tier 0. Second flag stops all runs. Both logged.

### 7.8 Write guards

| ID | Guard | AntCV origin |
|---|---|---|

## 8. Fact integrity pipeline (anti-hallucination)

### 8.1 Stages

| ID | Stage | Rule |
|---|---|---|
| FACT-01 | Ingest and hash | SHA-256 per file version and per span (page, paragraph, table cell). Spans are the only citable unit. |
| FACT-02 | Deterministic extraction | Dates, numbers, units, currencies, IDs, revisions, roles extracted by parsers with span references. The LLM never extracts a number. |
| FACT-03 | Fact register | Baseline facts per project (C5). Imports create candidates, never auto-merges. On conflict both values are kept and flagged. Metrics are never auto-overwritten. Gaps are listed for a person to fill. (AntCV: IMPORT-CONFLICT-001, IMPORT-GAP-001, `docs/plan/KERNEL-V2-AND-INGESTION.md`) |
| FACT-04 | Claim generation | LLM returns structured claims only. Every claim carries ≥ 1 span ID. Instruction: if the sources do not state it, return `NOT_FOUND`. Deterministic decoding (temperature 0 or equivalent). |
| FACT-05 | Evidence check | Cited span exists, hash matches current file version, quoted text appears verbatim after normalisation. |
| FACT-06 | Numeric fidelity | Every number, date, unit and currency in a claim appears in its cited span, or is derived by a declared formula that the verifier recomputes. A number must keep the noun it measured: no moving a figure to a different object. (AntCV: SOURCE-FRACTURES-001, METRIC-SEMANTIC-001) |
| FACT-07 | Cross-family entailment | A model from a different vendor family answers: "Does the claim state anything the cited spans do not?" Fails closed on a flagged claim. If the verifier call itself fails, the deterministic gates still hold and the claim is labelled UNVERIFIED, never VERIFIED. (AntCV: `verify_no_new_claims`, `scripts/job-tracker/density_fit.py`) |
| FACT-08 | Source fracturing | Writer and verifier receive the source in different orderings (e.g. writer: source order; verifier: facts grouped by kind or seeded shuffle). (AntCV: SOURCE-FRACTURES-001) |
| FACT-09 | Cross-document consistency | Same fact in more than one document (milestone date, budget, revision, owner role) is compared. A mismatch is a finding (conflict register, FACT-26). |
| FACT-10 | Freshness | Cited document is the latest released version. Citing a superseded revision is a finding. |
| FACT-11 | Locale check | Number, date, scale and unit interpretation per Sections 10–11. |
| FACT-12 | Labelling | See 8.2. |
| FACT-13 | Retry limit | A failing generation is retried at most twice with explicit fix instructions; the third result ships with `flagged: true` to the review queue, never silently. A retry after a fabrication veto may only remove content, never add. (AntCV: `writing-style-engine.js` retry loop; DENSITY-GROW-VETO-SHRINK-001) |
| FACT-14 | Garbled-input guard | If text extraction quality is low (garbled characters, wrong encoding, near-empty after whitespace collapse), the LLM is skipped. Route to OCR/vision or to a person, show a visible notice. (AntCV: JD-SCAN-HALLUCINATION-001, JOBTRACKER-ELIGIBILITY-CONTENT-LEN-001) |
| FACT-15 | Context isolation | Prompt examples carry shape only, never real facts. No fact from project X can appear in project Y's output; a cross-project string match runs on every report. (AntCV: EXAMPLE-ISOLATION-001, CL-GHOST-COMPANY-001) |

### 8.5 Import discipline for the fact register

- **FACT-16** The fact register outranks any prompt, template or stored routine text. When they disagree, the register wins and the disagreement is a finding. (AntCV: demand-seed incident, where a stored prompt hand-wrote rows with a flat weight; rule: the repo document outranks the stored prompt, and writes go through the shipped writer with a dry run first.)

### 8.6 Wording and claim discipline

- **FACT-17** Absolute or promise language ("guaranteed", "fully compliant", "zero risk", "will never") in a generated summary is blocked unless quoted verbatim from a source span. In source documents it is an S4 finding for the author.
- **FACT-18** Claim parity: when the same fact appears in two outputs (e.g. monthly summary and finding detail), the wording and attribution match. (AntCV: course-reviewer rule "claim parity" between CV and letter, `docs/personas/gabriel/CONTENT_RULES_2026-09-27.md`)
- **FACT-19** A banned-word list per language for generated text (empty promotional words). Kept in config, versioned, checked deterministically.

### 8.7 Words and phrases to avoid

- **FACT-21** Exceptions: a word inside a quoted span, a glossary-defined term, or a defined convention (e.g. "shall" defined in the document) is not flagged. Context rules cover legitimate uses ("significant" next to a stated test statistic).
- **FACT-22** Generated text never introduces a word-to-avoid the source does not contain. If the source uses one, the summary quotes it with attribution.

### 8.8 Ambiguity inside one document

- **FACT-23** Internal consistency checks per document:
  - same fact with different values (date in the summary vs the table; total in the text vs the sheet);
  - one term with two meanings, or two terms for one thing (glossary drift: "go-live", "launch" and "SOP" for one milestone);
  - unit, currency or scale switch mid-document;
  - acronym defined twice differently, or used before its definition;
  - broken internal references (missing "section 4.2"; "attached" with no attachment; skipped figure or table numbers);
  - revision stated differently in header, footer and change history.
- **FACT-24** Ambiguous claims:
  - comparative without baseline or period ("faster", "improved by 20 %");
  - claim without subject, time or measure ("performance improved");
  - relative time ("next Friday", "end of quarter", "in two weeks"), resolved against the document date and stored as ISO 8601 beside the original; unresolvable means a finding;
  - relative pointers ("the latest version", "as agreed", "the above") with no reference;
  - ambiguous numeric dates (INTL-01) and scale words (INTL-02, LANG-11);
  - pronouns in requirements that can bind to two subjects.
- **FACT-25** Method: rules first (pattern lists per language, date resolver, term index). The local LLM only classifies candidate spans; it never rewrites the source. Every flag cites the spans involved.

### 8.9 Conflicting documents

- **FACT-26** Conflict register. Each conflict holds the fact key, the spans and values in each document, document dates and authority rank. FACT-09 opens it. It stays open until a change record, a corrected document, or a reviewer decision with evidence closes it.
- **FACT-27** Authority hierarchy per project, configured in M4. Example default: signed contract > approved baseline or change record > released specification or drawing > plan > status report > minutes > working draft. The hierarchy marks which value is presumed current; it never deletes the other. Where the hierarchy does not decide, DAMC does not choose: both values go to the owner role.
- **FACT-28** Newer is not automatically right. A newer status report that contradicts an approved baseline with no change record is a finding (PM-05), not an update.
- **FACT-29** Cross-language conflicts (Danish minutes vs English plan) are compared on invariant fields only (LANG-01). Prose differences go to the language reviewer.
- **FACT-30** DAMC's own outputs are checked against the conflict register before release. A report may not state a value that is in an open conflict without naming the conflict.

### 8.10 Entailment checker (how FACT-07 is built)

- **FACT-31** The cross-family check in FACT-07 can be a dedicated natural-language-inference (NLI) classifier running locally. It labels each pair of cited span and claim as entailment, neutral or contradiction, with a score. It is a different model family from the generating LLM, small, offline and repeatable. Mapping: entailment above the calibrated threshold gives SUPPORTED (VERIFIED still needs the deterministic match, FACT-05/06); neutral gives UNVERIFIED; contradiction above the threshold gives a CONTRADICTED candidate for review.
- **FACT-32** Thresholds are calibrated per language and per check type on the gold set, never copied from a model card.
- **FACT-33** Route by span language (LANG-08). An English-only model never scores Danish, Swedish, Norwegian or Finnish spans. Nordic spans use a multilingual candidate that has passed the per-language gold set. If no candidate passes for a language, claims in that language stay UNVERIFIED and go to a person (no silent fallback, LANG-04). Translate-then-check is allowed only when the translation passes LANG-03, and the result is labelled as translated.
- **FACT-34** One claim against one cited span. Long spans are split into sentences or short windows, because NLI models are usually trained on short premise–hypothesis pairs. The best-scoring window counts; all window scores are logged.

## 9. Local mirrors

A local mirror is a read-only, dated, hashed snapshot of an external or company reference source, stored in Zone D. It lets the closed machine fact-check without browsing.

### 9.1 Mirror catalogue

| ID | Mirror | Content | Refresh |
|---|---|---|---|
| M1 | Regulatory text | EUR-Lex (AI Act, GDPR, NIS2, CRA, Machinery Regulation, dual-use, Data Act), national law portals (Section 10.6, 11.2) | Monthly diff |
| M2 | Language references | Company glossaries per language. Public dictionaries only where the licence allows bulk copy. | Monthly |
| M3 | Standards metadata | Number, title, edition, status (current / withdrawn / replaced). Not full text unless licensed: ISO/IEC standards restrict copying (MIR-07). | Monthly |
| M4 | Company references | Role list, project codes, document numbering scheme, gate checklists, QMS procedure index, approved templates | On change, max monthly |
| M5 | Calendars | Public holidays per country/site, ISO week calendars, fiscal-year definitions | Yearly + monthly check |
| M6 | Codes and units | ISO 4217 currencies, ISO 3166 countries, BCP 47 language tags, SI units and conversion tables for unit checks (INTL-03) | Quarterly |
| M7 | Build mirror | Approved packages and model weights, hash-pinned. Built with the controlled mirror pattern (Section 9.5). | Monthly check, per release |

### 9.2 Mirror rules

- **MIR-01** Every mirror has a manifest: source, retrieval date, licence, SHA-256 per file, version, owner role, next refresh date.
- **MIR-02** Refresh produces a diff against the previous snapshot. A person approves promotion. The previous version is kept so old runs stay reproducible.
- **MIR-03** Every finding that used a mirror cites the mirror ID and version.
- **MIR-04** A mirror past its refresh date downgrades dependent results to UNVERIFIED, reason "mirror stale".
- **MIR-05** Mirror hashes verified at each run start. Mismatch stops the run.
- **MIR-06** Mirrors that must stay identical to another copy have a drift test that fails on any difference. (AntCV: `pwa/test/relay-model-rates-mirror.test.mjs` fails when the three price tables drift; proxy/demo-proxy byte parity.)
- **MIR-07** Licence check before mirroring. Many dictionaries and all ISO/IEC standards restrict copying.
- **MIR-08** A value that "sounds verified" is not verified. Prices, dates and legal references in mirrors are diffed mechanically against the fetched source at each refresh. (AntCV: a wrong price survived three review passes because its comment sounded verified, `docs/qa/COST_QUALITY_WEEKLY_2026-10-23.md`.)
- **MIR-09** An unreadable source is recorded as "unreadable", never as "no change". (AntCV: JOBSRC-FETCH-001, where unreadable sources looked like dry sources.)

### 9.3 Local mirror of OneDrive state

- **MIR-10** DAMC keeps a local index of the files it scanned: file ID, path, version/eTag, hash, last scan, last finding set. Pulled by revision, rebuilt when needed. Local-only annotations are kept; DAMC never pushes them back to source files. (AntCV: local Excel mirror of the cloud job tracker, pulled by revision, push-back owner-gated, `docs/qa/REGISTER_RUNLOG.md`.)
- **MIR-11** Fact register changes are staged without destroying the old version: new version stored beside the old one, readers migrated, prior data backed up. (AntCV: kernel v2 migration, `docs/plan/KERNEL-V2-AND-INGESTION.md`.)

### 9.4 One-way import

- **MIR-12** The closed machine never browses. Refresh: a separate connected step downloads sources, scans them, builds the manifest; files move to the closed machine through a controlled transfer; the closed machine verifies hashes and licences before promotion.

### 9.5 Controlled internal package mirror (pattern)

Owner example, 2026-11-05, written for `pypdf`. The same pattern applies to every third-party component that reads document content or runs a model.

## 10. Scandinavian language fact-check

### 10.1 Core rule: meaning first, language second

- **LANG-01** Facts are language-neutral. Each field is either **invariant** (copied byte for byte: numbers, dates, proper nouns, standard names such as ISO 9001, FMEA, IDs, codes) or **translatable** (prose, labels, headings). (AntCV: `docs/qa/BABEL_FISH_LANGUAGE_ARCHITECTURE.md`)
- **LANG-02** Analysis runs on the source language. Translation is a reviewer aid only, marked as machine translation.
- **LANG-03** After any translation, compare the list of numbers and all-caps acronyms before and after. Two or more missing: translation rejected. (AntCV: same file.)
- **LANG-04** No silent fallback. An unsupported language returns `unsupported_language`, and the document goes to Tier 0 plus a person. (AntCV: `skills/antcv-writer/references/language-output.md`)
- **LANG-05** Output language follows the source document, not the UI setting. (AntCV: output language follows the job ad.)
- **LANG-06** No mixed-language output in one generated text. Labels keyed in English internally, displayed in the target language; a label already in the target language is left alone. (AntCV: WHO-LANG-001, FOUNDATION-LANG-001)
- **LANG-07** Nordic text processing uses UTF-8 end to end and file-based scripts. AntCV saw every Nordic term count read 0 % because an inline shell one-liner mangled æøå/åäö.

### 10.2 Language identification

- **LANG-08** Per-paragraph language ID (`da`, `sv`, `nb`, `nn`, `fi`, `is`, `en`). Mixed documents are normal; record each span's language.
- **LANG-09** Danish versus Norwegian Bokmål is the main confusion risk. Use a dedicated discriminator, not a generic detector. Marker examples: da *af, hvad, nu, købe, efter, spørgsmål* vs nb *av, hva, nå, kjøpe, etter, spørsmål*; sv *och, inte, är*, letters ä/ö. AntCV's own detector separated only Danish from English (stopword ratio > 1.15× and ≥ 5 hits) and never auto-detected Swedish — a gap DAMC MUST close.

### 10.3 Number, date, currency conventions

| | Denmark | Sweden | Norway | Finland |
|---|---|---|---|---|
| Decimal mark | comma | comma | comma | comma |
| Thousands | point: 1.000.000 | space: 1 000 000 | space: 1 000 000 | space: 1 000 000 |
| Common date | 05.11.2026 / 5. november 2026 | 2026-11-05 / 5 november 2026 | 05.11.2026 / 5. november 2026 | 5.11.2026 |
| Currency | DKK, "kr." | SEK, "kr" | NOK, "kr" | EUR, "€" |
| Week label | uge 45 | vecka 45 (v. 45) | uke 45 | viikko 45 |

Checks:

- **LANG-10** "1.000" is one thousand in a Danish span and one in an English span. Parse by span language, not document default.
- **LANG-11** Scale words: Danish/Norwegian *milliard*, Swedish *miljard* = 10⁹; Danish/Norwegian/Swedish *billion* = 10¹². English *billion* = 10⁹. A translated budget that changes scale is S1.
- **LANG-12** ISO week numbers are standard in Nordic planning. Check week number against date (2026-11-05 is ISO week 45, Thursday). US-style week numbering differs.
- **LANG-13** "kr" alone is ambiguous across DKK/SEK/NOK. Resolve from context or flag.
- **LANG-14** Public holidays come from mirror M5, never from model memory. Example trap: Danish Store Bededag stopped being a public holiday from 2024 `[V]`; schedules built on older calendars are wrong.

| Norway | Organisasjonsnummer: 9 digits, modulus-11 | Fødselsnummer: 11 digits |
| Finland | Y-tunnus: 7 digits + check digit (1234567-8) | Henkilötunnus: DDMMYY + century sign + 3 digits + check character (DDMMYYCZZZQ) |

- **LANG-16** VAT number formats: DK + 8 digits, SE + 12 digits, FI + 8 digits; Norway uses the organisation number + "MVA" and is outside the EU VIES system.

### 10.5 False friends and PM terminology

| Term | Language | Means | Common wrong reading |

### 11.4 Scope expansion step (mandatory)

Owner instruction 2026-11-05: whenever a country, region, site, language or legislation is added to DAMC's scope, DAMC is first expanded to fit that scope's laws, standards, norms and culture. The step is always documented.

- **INTL-14** Every addition to the scope runs the expansion step before any rule for it goes live. There are no exceptions for small additions. The step produces an expansion record (Section 11.5), kept in the system documentation set (Section 16.3).
- **INTL-15** The expansion covers every dimension in the table below, not only the law. A dimension that does not apply is marked "not applicable" with a reason, never left blank.
- **INTL-16** Culture and business-practice rules describe documented practices: approval steps, sign-off conventions, how decisions and deadlines are written. They come from company material or a named local reviewer. They never describe national character or rely on stereotypes. They are reviewed yearly.
- **INTL-17** Until the expansion record is signed, documents from the new scope run at Tier 0 only, and any finding that depends on the new scope's rules is labelled UNVERIFIED.

Order of work:

1. Owner role named; expansion record opened.
2. Legislation answered by Legal: request L-01 sections A–G repeated for the new scope, with local counsel where Legal asks for it.
3. Standards, norms and business conventions collected, each with its source.
4. Mirrors and locale parsers built; unit tests written.
5. Tools selected per language (FACT-33, MON-12).
6. Gold-set cases added; release gates pass (Section 15.4).
7. Reviewers named; DPIA checked for the new scope; AI compliance lead signs.
8. Pack switched on in config (two-person change).
9. From the next monthly cycle, the regulatory watch and the tool watch include the new scope.

A legislation-only addition (for example a new EU act) runs the same step. Dimensions that do not change (language, calendar) are marked "not applicable" with the reason.

## 14. Academy knowledge layer

"Academy" here follows AntCV usage: the Improve Business Academy course whose checklists and reviewer feedback AntCV turned into machine rules. DAMC copies the method, not the CV content.

### 14.1 Checklist conversion method

- **ACAD-01** Every training checklist, QMS procedure or gate checklist is converted into checks with four outcomes: **OK**, **WARN**, **FAIL** where text can decide, **MANUAL** where only a person can. MANUAL items are listed for the reviewer, never guessed. (AntCV: `scripts/job-tracker/course_checklist.py` converts the course's 8-group CV checklist this way, runs after every generation, never blocks generation, exits 1 on FAIL.)
- **ACAD-02** Thresholds are explicit and versioned (AntCV example: keyword coverage ≥ 60 % OK, 40–59 % WARN).
- **ACAD-03** The checker reads the finished artifact (PDF, DOCX, XLSX), so it works on any document, not only on DAMC outputs.

### 14.2 Feedback to rules

- **ACAD-04** Reviewer and trainer feedback becomes a rule only through the register: finding → rule proposal → gold-set case → release. (AntCV: course reviewer feedback became engine rules, e.g. no promises, fixed order, claim parity.)
- **ACAD-05** Rules are pure functions shared by the UI and the unit tests, so the console and the test suite cannot disagree. (AntCV: `pwa/antcv-profile-rules.js`.)
- **ACAD-06** A single machine-readable rules file is the control site. The written rules document outranks the code; when they disagree, the document wins and a defect is raised. (AntCV: `docs/qa/GOLD_STANDARD_LOCKER.md`, `pwa/gold-rules.json`.)
- **ACAD-07** Every rule has a kill switch.

### 14.3 Knowledge base and training

- **ACAD-08** Knowledge base entries: rule, rationale, source (law, standard, procedure, incident), example pass, example fail, owner role, review date.
- **ACAD-09** AI literacy course (AIA-02) built from the knowledge base: hallucination types seen in DAMC's own gold set, verification labels, NG list, how to reject a finding, how to report an incident. AntCV's compliance file used the Academy's AI-ethics course deck as a source; DAMC should do the same with the company's chosen training material.
- **ACAD-10** Reviewed lessons (PM-12) feed the knowledge base, tagged by phase and domain (PM, HW, language, region).
- **ACAD-11** Monthly: top recurring finding types become a short "what we saw" note for project teams. Role-level only (NG-1).

## 15. QA framework

### 15.1 Test levels

| Level | Scope | When |
|---|---|---|
| Unit | Parsers, locale number/date parsing, check-digit validators, unit conversion, each rule | Every change |
| Integration | Connector → report on synthetic projects | Every change |
| Gold set | LLM-backed checks against expected answers | Every change to model, prompt, rule, mirror; monthly regardless |
| Adversarial | Injection, PII, export-control, garbled input, cross-project leakage | Same as gold set |
| Identity | Rebuild/refactor reproduces previous outputs exactly | Every rebuild (SEC-13) |
| Acceptance | Reviewers on a pilot project | Each phase exit |

### 15.2 Gold set

- **QA-01** Synthetic data only. No real personal data. (AntCV: synthetic persona rule in `CLAUDE.md`, `docs/personas/anita/`.)
- **QA-02** Start at ≥ 100 cases, grow with every confirmed defect. Categories: true facts; planted contradictions; planted numeric errors; number moved to the wrong noun; missing evidence; superseded revisions; Danish/Norwegian confusion; Danish thousands point; scale words (billion, 万, lakh); ambiguous dates; FY labels; unit mix; prompt-injection documents; PII and national IDs; export-control markings; garbled OCR; empty-but-long documents; cross-project leakage bait; a human file carrying a forged "generated by" tag (write must be refused); a generated file edited by a person (no overwrite, new revision); words-to-avoid per category and language, including a quoted and a glossary-defined use that must not be flagged; one document with two values for one fact; relative dates; two documents in conflict with and without an authority-hierarchy answer; an overridden finding later confirmed by evidence; entailment, neutral and contradiction pairs per language (en, da, sv, nb, fi) for the entailment checker and tool watch.
- **QA-03** Every check has a negative control: the gold set contains a case the check must fail, and a test proves it fails.

### 15.3 Gold locker

- **QA-04** Gold set and expected answers are frozen, versioned and hashed. Changes need two-person approval and a reason. (AntCV: `docs/qa/GOLD_STANDARD_LOCKER.md`.)
- **QA-05** No "done" claim before a per-item audit. Failures are named per item, never summarised away.

### 15.4 Release gates

All MUST pass:

1. Unit and integration tests green.
2. Gold-set metrics at or above Section 8.4 targets.
3. No regression on any previously fixed case.
4. Identity gate (for rebuilds).
5. Security scans clean or exceptions signed.
6. This document and the system card updated.
7. Version stamps agree across config, rules, prompts, mirrors and model (one check script fails the release otherwise — the AntCV cache-bust gate pattern, `scripts/check-cache-bust.mjs`).

### 15.5 Human review sampling

- **QA-06** 100 % review of S1, S2 and CONTRADICTED. SUPPORTED claims: 20 % sample in months 1–3, then 10 %. Sample drawn at random by the tool, not chosen by the operator.
- **QA-07** Reviewer can downgrade or reject. Upgrading a label needs new evidence.
- **QA-08** Quarterly calibration: two reviewers score the same sample; agreement recorded.

### 15.6 Defect register

- **QA-09** IDs in the form `DAMC-<AREA>-<NAME>-NNN` (e.g. `DAMC-FACT-SCALEWORD-001`). Each entry: symptom, reproduction, root cause, rule or code change, gold-set case added, verified date. Separate active and closed registers. Each active row carries one `verified:` date; monthly runs check the stalest rows first. (AntCV: `docs/qa/OPEN_REGISTER.md`, `docs/qa/ACTIVE_BUGS.md`.)
- **QA-10** A tooling bug that blocks measurement is S1 for the QA system itself. (AntCV: a single log line to stdout corrupted the harness JSON and quietly stopped measurement, CL-RENDER-HARNESS-STDOUT-001.)

### 15.7 Report preflight

**QA-11** Before sign-off, the reviewer runs the preflight list (Section 22.3). Built from the authoritative fact register, measured not eyeballed, stale outputs deleted before re-render, diffed against the previous month's report.

### 15.8 Learning from reviewer disagreement

Scope: every module (PM, HW, language, region, mirrors, generated text). A user who contradicts a finding is a learning signal for the tool, and sometimes for the reviewer.

| ID | Rule |
|---|---|
| LEARN-01 | Every reject, downgrade or override records a reason category plus free text and, where possible, an evidence link. Categories: rule wrong; wrong span or parse; context the tool lacks; source wrong but risk accepted; correct but not relevant; duplicate. |
| LEARN-02 | Disagreement is data, not truth. The reviewer can be wrong. Overriding an S1, S2 or CONTRADICTED finding needs evidence or a second reviewer. An override without evidence is stored as "risk accepted", never as "false positive". |
| LEARN-03 | Edits to generated text count as disagreement too. The diff is stored with source, actor role, reason, confidence and risk. (AntCV: `change_log` fields, DOC-05.) |
| LEARN-04 | Monthly aggregation per check: override rate and reason mix. A check above the review trigger (> 30 % over ≥ 20 findings) goes to rule review. Small samples change nothing. (AntCV: a run with n = 4 was judged too small to change any rank; the cost-quality tune needs a minimum of 20 calls.) |
| LEARN-05 | Reverse check: when later evidence confirms a finding that was overridden (the milestone did slip, the revisions did differ), the override is reopened and marked "override contradicted by evidence". This feeds reviewer calibration (QA-08) and the AI literacy material (ACAD-09). |
| LEARN-06 | No automatic learning. No online fine-tuning, no automatic threshold changes. Every change goes finding → register → rule proposal → gold-set case → release (ACAD-04), at most one change per check per cycle, with hysteresis (MON-05). |
| LEARN-07 | Repeated overrides with the same reason become a knowledge-base entry (ACAD-08), e.g. a project-specific term, an accepted local convention, an authority-hierarchy exception (FACT-27). |
| LEARN-08 | A user disputing a mirror value (holiday, legal reference, glossary term) triggers a source check (MIR-08), not a local edit. |
| LEARN-09 | Privacy and NG-1. Disagreement statistics are kept per check and per reviewer role, never as a per-person accuracy ranking. Calibration results are reported in aggregate. Reviewer identity in the learning data is a keyed hash, used only to detect duplicates. Under the AI Act, monitoring or evaluating workers would make DAMC high-risk. |
| LEARN-10 | The monthly summary reports: checks under review, rules changed, overrides reopened by evidence, top override reasons. |

Yearly: external audit or pen test, AI Act and GDPR re-assessment, retention clean-up audit.

### 17.2 Run hygiene

- **MON-01** Every run writes a start heartbeat and an end heartbeat. Start without end raises an alarm. A scheduled run that did not fire raises an alarm. (AntCV rule 0, `docs/qa/SCHEDULED_ROUTINES.md`.)
- **MON-02** "No findings" and "scan failed" are different states and are shown differently. Zero files read is a failure. (AntCV: an empty telemetry window is not an outage, and an outage is not an empty window; tell them apart with heartbeats.)
- **MON-03** A run's result is complete only when written to the register and the register check passes.
- **MON-04** Health signals must see bad output, not only uptime. A model returning malformed, empty or wrong-language output lowers its health score. (AntCV: RELAY-DETECTION-GAP-001.)

### 17.3 Operational metrics

Run success rate, duration, files scanned, intake failures, Tier routing counts, LLM calls and tokens (metadata only), cost (Tier 2), abstain rate, pre-gate unsupported rate, reviewer rejection rate, mirror freshness, guard refusals, injection detector hits.

### 17.4 Model and configuration tuning

- **MON-05** Model or prompt changes follow the AntCV weekly tune pattern, run monthly here: score = gold-set pass rate (cost as secondary), quality floor ≥ 0.90 on the gold set, minimum sample size before any change, at most one change per role per cycle, keep the current choice unless clearly beaten (hysteresis), never remove the fallback, record the rollback value, apply only with owner approval. (AntCV: `docs/qa/COST_QUALITY_WEEKLY_2026-10-23.md`.)
- **MON-06** Cost is recomputed from raw counts each cycle, not trusted from stored values.
- **MON-07** A tuning run on empty or stale data reports **BLIND** and changes nothing. (AntCV: the tune script exits with a BLIND status when telemetry is empty or stale; server-side calls had gone unlogged for weeks before LLM-LOG-SERVER-001.)

### 17.5 Tool watch (part of monitoring and of every monthly cycle)

- **MON-08** Every month, look for better tools. Scope: entailment and fact-check models, the generating LLM, OCR, document parsers, language ID, spelling and terminology resources, mirror sources.
- **MON-09** Tool register, per component: current tool and version; candidates; where each was found (model hub, paper, vendor release, internal tip); licence status; last evaluation date; gold-set scores per language and per check type; decision and reason. Rejected candidates stay listed with the reason and are re-tested only on a new version or a new gold-set category.
- **MON-10** Candidates enter only through the controlled mirror (MIR-13 to MIR-17). They are evaluated offline in the evaluation sandbox (request IT-05, item 10), never first on live project data.
- **MON-11** Adopt only when the candidate beats the current tool on the gold set beyond the set margin, with no drop on any gate metric (Section 8.4) and a clean adversarial run. One component change per cycle. The previous tool stays as fallback for one full cycle, with the rollback recorded (MON-05).
- **MON-12** A tool better in one language and worse in another is adopted for that language only (routing, FACT-33).
- **MON-13** First register entry: English entailment checker. Current: none. Candidates: `MoritzLaurer/DeBERTa-v3-large-mnli-fever-anli-ling-wanli` (preferred, owner observation) and FactCG (lower priority for English). Nordic entailment checker: to be selected (Section 8.10).

## 18. Change control and release

- **CHG-01** Sync first, claim a lane (version range), work in an isolated branch or worktree, release the lane at the end. One deployer at a time. (AntCV: `scripts/shift.mjs`, `docs/qa/NIGHT_SHIFT.md`.)
- **CHG-02** Never force-push or reset away shared history. A rejected push is rebased, then pushed.
- **CHG-03** Diagnostic-first for any fix: reproduce → probe → targeted change → regression case. No speculative edits to the guard chain or the LLM gateway.
- **CHG-04** One owner per component during a change; no parallel session commits over a confirmed fix from a stale base.
- **CHG-05** Every release bumps and cross-checks all version stamps (15.4 step 7).
- **CHG-06** Rollback plan stated per release. Previous mirrors, rules and model kept until the next release passes one full monthly cycle.
- **CHG-07** Documentation-only changes skip the lane claim but still sync first.
- **CHG-08** Local hooks are convenience. The same checks run again on the server side for every pull request, because local hooks do not run for changes made elsewhere. (AntCV: CACHE-BUST-PR-GATE-001, `.github/workflows/pr-gate.yml`.)
- **CHG-09** Local hooks may fail open on an infrastructure error, with a warning. Release gates always fail closed.
- **CHG-10** Deployment defaults to dry run, requires typing the target name to confirm, and allows one deployment per target at a time without cancelling a running one. (AntCV: `deploy.yml`.)
- **CHG-11** One lane claim per working copy. A shared session ID let one release delete another session's claim.
