## Why "auto-shift" rather than "auto-resolve"

Per plan §4.6, conflicting chips "move the style to Hybrid Balanced (or Custom Tone) automatically." This PR implements the Hybrid Balanced path. The alternative ("Custom Tone") would create a brand-new ad-hoc style at the moment of conflict, which is a bigger UX shift and not part of the writing-system registry. Hybrid Balanced already has the right `defaultToneChips` (`bridging`, `dual-register`, `jd-tuned`) and `primaryConstraint` (`bridging two registers`) to carry conflicting chips coherently, so it's the more conservative landing point.

## Why we don't auto-reset on chip removal

Once the user has switched to Hybrid Balanced (manually or via auto-shift), removing the conflicting chip does NOT auto-revert the style. The signal is: the user accepted Hybrid Balanced, and any further chip changes stay within that style unless they manually change the dropdown. This avoids ping-ponging the active style as chips toggle.
